# 蓝牙域端到端延迟与网页启停功能完整修改方案

## 1. 文档目标

本文给出蓝牙域以下两项功能的完整改造方案：

1. 计算从发送电脑生成报文开始，到云端接收报文为止的真实端到端延迟；
2. 网页上的“打开发送/关闭发送”命令经过完整硬件链路到达发送电脑，并实际启停 `ble_s32_sender.py`。

改造后的基本约束是：

- 运行 `ble_s32_sender.py` 的电脑不得与云端建立 HTTP、WebSocket 或其他直接链路；
- 发送电脑只允许通过 BLE 与 nRF52840 通信；
- 云端地址和 `VEHICLE_INGEST_TOKEN` 只保存在 Jetson；
- 控制成功必须以发送电脑真实执行命令并返回 ACK 为准，不能以 Jetson 完成 UDP `sendto()` 为准；
- 延迟时间戳或时钟同步信息必须经过 BLE、UART、K3、以太网、Jetson 和 HTTP 链路，不能通过独立 HTTP 旁路登记。

本文中的固定地址和端口如下：

| 节点 | 地址/端口 | 用途 |
|---|---|---|
| Jetson `eno1` | `192.168.4.100/24` | 板端网络接口 |
| 蓝牙 K3 板 | `192.168.4.20` | 蓝牙域以太网节点 |
| K3 → Jetson | UDP `5000` | 遥测、同步响应、控制 ACK 上行 |
| Jetson → K3 | UDP `5001` | 控制命令和时间同步请求下行 |
| BLE Write | `00001001-0000-1000-8000-00805f9b34fb` | 发送电脑向 nRF52840 写入数据或响应 |
| BLE Notify | `00001002-0000-1000-8000-00805f9b34fb` | nRF52840 向发送电脑下发控制或同步请求 |

### 1.1 强制分阶段原则

本方案不并行开发网页启停和端到端延迟，必须按以下顺序推进：

```text
当前阶段：发送端解除云端直连，网页只预留两个辅助功能
  → 当前阶段验收通过
  → 第一阶段：网页启停真实闭环
  → 阶段一验收门通过
  → 第二阶段：时钟同步与端到端延迟
```

当前阶段只保留蓝牙正常/异常报文发送、BLE 重连、K3/Jetson 转发、云端采集和
异常检测等核心功能。网页启停按钮保持禁用，延迟显示“待接入”；发送电脑不
调用任何云端 HTTP 接口。该阶段不实现控制下行、真实 ACK、时间同步和延迟计算。

第一阶段只解决“网页命令能否经过完整硬件链路实际启停发送”问题。该阶段应同时删除发送电脑到云端的全部 HTTP 访问，包括旧 `/bluetooth/timing` 调用；在第二阶段完成前，网页延迟字段显示“待时间同步”或“不可用”，不得继续使用旧 HTTP 旁路计算延迟。

第二阶段只能在以下条件全部满足后开始：

- 网页 ON/OFF 命令已经经过云端、Jetson、K3、nRF52840 和 BLE 到达发送电脑；
- `ble_s32_sender.py` 已实际启停业务报文；
- 真实 ACK 已沿原硬件链路返回云端；
- 拔掉 BLE 或 K3 网线时，网页不会错误显示执行成功；
- 发送电脑上抓包确认不存在任何云端 HTTP 流量。

## 2. 改造前实现存在的问题

改造前 `bluetooth_gateway/ble_s32_sender.py` 同时承担 BLE 发送和云端 HTTP 客户端职责：

- 通过 `/bluetooth/timing` 直接向云端登记发送时间；
- 通过 `/bluetooth/control/next` 直接轮询网页命令；
- 通过 `/bluetooth/control/ack` 直接向云端确认命令执行结果。

因此当前实际存在两条旁路：

```text
延迟旁路：发送电脑 ---------------- HTTP /timing ----------------> 云端

控制旁路：发送电脑 <---------- HTTP control/next、ack ----------> 云端
```

业务报文虽然经过以下硬件链路：

```text
发送电脑
  → BLE Write
  → nRF52840
  → UART
  → 蓝牙 K3 板（192.168.4.20）
  → Ethernet UDP 5000
  → Jetson（192.168.4.100）
  → HTTP
  → 云端
```

但延迟起点和控制命令没有经过这条完整链路。由此产生以下问题：

- 发送电脑必须知道云端地址并持有上传 Token；
- HTTP 时间登记成功不代表 BLE 报文成功发出；
- 相同文本重复发送时可能发生时间登记关联错误；
- nRF52840、K3 或 Jetson 断开时，发送电脑仍可能收到网页控制；
- 网页显示成功不能证明完整硬件链路可用。

## 3. 目标总体架构

### 3.1 数据与延迟上行

```text
ble_s32_sender.py
  → BLE Write：遥测 + SEQ + TICK_US + SYNC_ID
  → nRF52840
  → UART
  → K3
  → UDP 5000
  → bluetooth_edge_agent.py
  → 根据 SYNC_ID 将 TICK_US 映射为 source_time_ms
  → HTTP 上传
  → run_cloud.py
  → 计算 cloud_received_at_ms - source_time_ms
  → 网页显示端到端延迟
```

### 3.2 网页控制下行与真实 ACK 上行

```text
网页点击“打开发送/关闭发送”
  → 云端保存命令
  → Jetson 轮询命令
  → UDP 5001
  → K3
  → UART
  → nRF52840
  → BLE Notify
  → ble_s32_sender.py 实际修改 enabled
  → BLE Write 返回 ACK
  → nRF52840
  → UART
  → K3
  → UDP 5000
  → Jetson
  → HTTP ACK
  → 云端更新状态
  → 网页显示成功或失败
```

## 4. 第二阶段技术设计：端到端延迟

本节仅在第一阶段网页启停闭环验收通过后实施。第一阶段不实现本节的 `BTSYNC`、时钟映射和延迟计算。

### 4.1 为什么不能直接使用发送电脑的系统时间

如果直接在报文中加入发送电脑的 `time.time()`，计算公式为：

```text
E2E = 云端接收时间 - 发送电脑系统时间
```

该方案要求发送电脑和云端时钟已经同步。发送电脑被限制为只能连接 BLE 后，不能依赖它直接访问 NTP 或云端校时。时钟偏差会被错误地计入网络延迟。

因此推荐使用：

- 发送电脑只记录单调时钟 `monotonic_ns()`；
- Jetson 经完整反向硬件链路发起四时间戳同步；
- Jetson维护“发送电脑单调时钟 → Jetson epoch 时间”的映射；
- 云端与 Jetson 使用正常系统 NTP 保持同步。

### 4.2 四时间戳同步流程

每次同步使用四个时间点：

| 时间点 | 记录位置 | 含义 |
|---|---|---|
| `T1` | Jetson | Jetson 发出同步请求的 epoch 毫秒 |
| `U2` | 发送电脑 | BLE Notify 收到请求的 monotonic 微秒 |
| `U3` | 发送电脑 | BLE Write 发出响应前的 monotonic 微秒 |
| `T4` | Jetson | Jetson 收到同步响应的 epoch 毫秒 |

完整路径如下：

```text
Jetson T1
  → UDP 5001
  → K3
  → UART
  → nRF52840
  → BLE Notify
  → 发送电脑 U2/U3
  → BLE Write
  → nRF52840
  → UART
  → K3
  → UDP 5000
  → Jetson T4
```

Jetson计算：

```text
电脑时钟中点 = (U2 + U3) / 2 / 1000
Jetson时钟中点 = (T1 + T4) / 2
offset_ms = Jetson时钟中点 - 电脑时钟中点

round_trip_ms = (T4 - T1) - (U3 - U2) / 1000
```

发送电脑后续报文携带 `TICK_US`。Jetson重建发送时间：

```text
source_time_ms = TICK_US / 1000 + offset_ms
e2e_latency_ms = cloud_received_at_ms - source_time_ms
```

### 4.3 同步质量控制

Jetson只采用满足以下条件的同步结果：

- `SYNC_ID` 与尚未完成的同步请求一致；
- `T4 >= T1` 且 `U3 >= U2`；
- `round_trip_ms` 在 `0～500 ms` 范围内；
- 同步映射不超过 30 秒；
- 连续同步结果的 offset 跳变不超过配置阈值；
- 多次结果中优先采用 RTT 最小的样本，以降低上下行不对称误差。

建议参数：

| 参数 | 建议值 |
|---|---:|
| 同步周期 | 5 秒 |
| 映射有效期 | 30 秒 |
| 单次响应超时 | 2 秒 |
| 最大有效 RTT | 500 毫秒 |
| 保留同步样本 | 最近 8 个 |

如果没有有效同步映射：

- 遥测报文仍然上传；
- `e2e_latency_ms` 必须显示为不可用；
- 可以单独显示 `Jetson UDP 接收 → 云端` 延迟；
- 禁止使用 Jetson 接收时间冒充发送电脑的源时间。

### 4.4 遥测报文格式

为减少对现有业务文本的影响，建议采用分号键值字段：

```text
S32K344_HELLO_01;SEQ=1024;TICK_US=638251234567;SYNC_ID=87#
```

异常报文示例：

```text
S32K344_ABNORMAL_0003;TYPE=BLE_ATTACK;LEVEL=HIGH;SEQ=1025;TICK_US=638253234567;SYNC_ID=87#
```

字段定义：

| 字段 | 类型 | 说明 |
|---|---|---|
| `SEQ` | uint32 | 发送端递增序号，重连后可继续或重新建立会话 |
| `TICK_US` | uint64 | 写入 BLE 前尽可能靠近发送动作采集的单调时钟微秒 |
| `SYNC_ID` | uint32 | 该报文使用的最近一次同步映射编号 |
| `#` | 分隔符 | 完整帧结束标记 |

时间戳必须在获取 BLE 写锁之后、第一次 `write_gatt_char()` 之前生成，避免把排队等待时间漏掉。

## 5. 第一阶段技术设计：网页启停控制

本节是项目的首要实施范围。完成本节前，不开始第 4 节的时间同步开发。

### 5.1 控制命令格式

Jetson发往 K3 的命令：

```text
BTCTL|1|<COMMAND_ID>|SET_TX|ON|<ISSUED_AT_MS>|<NONCE>|<CRC16>#
BTCTL|1|<COMMAND_ID>|SET_TX|OFF|<ISSUED_AT_MS>|<NONCE>|<CRC16>#
```

示例：

```text
BTCTL|1|15|SET_TX|OFF|1791950000123|8F3A21C4|7B2E#
```

发送电脑执行后返回：

```text
BTACK|1|<COMMAND_ID>|APPLIED|ON|<TICK_US>|<CRC16>#
BTACK|1|<COMMAND_ID>|APPLIED|OFF|<TICK_US>|<CRC16>#
BTACK|1|<COMMAND_ID>|ERROR|<CURRENT_STATE>|<TICK_US>|<CRC16>#
```

首版实现如果固件资源有限，可以先使用无 CRC 的简化格式联调：

```text
CTRL:<COMMAND_ID>:ON#
CTRL:<COMMAND_ID>:OFF#
ACK:<COMMAND_ID>:APPLIED:ON#
ACK:<COMMAND_ID>:APPLIED:OFF#
```

正式验收版本应至少包含：协议版本、命令 ID、动作、随机数/会话标识和校验码。

### 5.2 发送端执行规则

`ble_s32_sender.py` 收到控制命令后必须：

1. 校验帧边界、协议版本、CRC 和命令字段；
2. 根据 `COMMAND_ID` 做幂等处理；
3. `ON` 时将 `enabled=True`，`OFF` 时将 `enabled=False`；
4. 状态修改完成后返回 `APPLIED` ACK；
5. 对重复命令不重复改变状态，但必须重发同一结果 ACK；
6. 未识别命令返回 `ERROR`，不能静默标记成功；
7. `OFF` 只停止业务遥测，不能停止 BLE Notify、控制 ACK 和时间同步响应；
8. BLE 断开后自动重连，重连后默认状态由配置决定，建议保持进程内最后状态。

控制 ACK 与业务报文共用 BLE Write 时，必须使用同一异步写锁，避免分片交叉。

### 5.3 Jetson命令投递规则

`bluetooth_edge_agent.py` 应维护每条命令的本地状态：

```text
queued → delivering → applied
                   ↘ error
                   ↘ expired
```

处理规则：

- 每 0.5 秒从云端获取待执行命令；
- 将命令发往 `192.168.4.20:5001`；
- 在未收到发送电脑 ACK 前，以相同 `COMMAND_ID` 重试；
- 建议重试间隔为 0.5、1、2、2、2 秒；
- 总超时建议为 10 秒；
- 仅收到匹配 `COMMAND_ID`、动作和会话的 ACK 后，才向云端提交 `applied`；
- 超时、格式错误或状态不一致时提交 `error`；
- K3 的 UDP 接收确认或 nRF 的 UART 接收确认只能作为链路诊断，不能作为最终成功 ACK。

### 5.4 网页状态语义

网页按钮点击后应显示真实状态，不应立即切换为成功：

| 状态 | 页面文案示例 |
|---|---|
| `queued` | 关闭命令已排队 |
| `delivering` | 正在通过 Jetson/K3/nRF 下发 |
| `applied` | 发送端已关闭 |
| `error` | 命令执行失败 |
| `expired` | 命令超时，未收到发送端确认 |
| 控制代理离线 | Jetson 蓝牙控制代理未连接 |

只有 `BTACK ... APPLIED` 到达云端后，按钮状态才能稳定显示“已打开”或“已关闭”。

## 6. 同步协议格式

Jetson发出的同步请求：

```text
BTSYNC|1|<SYNC_ID>|REQ|<T1_EPOCH_MS>|<CRC16>#
```

发送电脑响应：

```text
BTSYNC|1|<SYNC_ID>|RESP|<T1_EPOCH_MS>|<U2_MONO_US>|<U3_MONO_US>|<CRC16>#
```

示例：

```text
BTSYNC|1|87|REQ|1791950000123|A17C#
BTSYNC|1|87|RESP|1791950000123|638251100000|638251101200|C51D#
```

同步报文和控制报文需要最高优先级，不能因为业务发送被关闭而停止。

## 7. 各组件修改清单

### 7.1 `bluetooth_gateway/ble_s32_sender.py`

必须删除：

- `CLOUD_HTTP_URL`；
- `VEHICLE_INGEST_TOKEN`；
- `VEHICLE_ID`；
- `cloud_request()`；
- `register_send_time()`；
- `cloud_control_loop()`；
- `urllib` 和云端 JSON 请求相关依赖。

必须新增：

- BLE Notify UUID 配置；
- Notify 分片缓存和 `#` 帧重组；
- 控制命令解析、幂等缓存和真实状态修改；
- 同步请求处理；
- ACK/同步响应发送队列；
- 全局 BLE 写锁；
- `SEQ`、`TICK_US` 和 `SYNC_ID` 字段；
- 重连后重新订阅 Notify；
- 明确打印“发送端未配置任何云端地址”。

建议保留的配置只有：

```text
BLE_ADDRESS
BLE_WRITE_UUID
BLE_NOTIFY_UUID
BLUETOOTH_SEND_INTERVAL_SECONDS
BLUETOOTH_ABNORMAL_EVERY
BLUETOOTH_INITIAL_ENABLED
```

### 7.2 `jetson_edge/bluetooth_edge_agent.py`

在当前 UDP 5000 遥测上传功能上新增：

- 云端控制轮询线程；
- UDP 5001 控制与同步发送；
- UDP 5000 报文分类：`BTDATA`、`BTACK`、`BTSYNC RESP`；
- 待执行命令表、重试、超时和幂等处理；
- 同步样本表及 `offset_ms` 计算；
- 将 `TICK_US + offset_ms` 转换为 `source_time_ms`；
- 只有收到真实 ACK 后才调用云端控制 ACK；
- 来源地址校验，只接受蓝牙板 `192.168.4.20` 的控制 ACK 和同步响应；
- 线程间安全队列，避免控制轮询阻塞 UDP 接收和遥测上传。

### 7.3 `jetson_edge/start_edge.py`

向蓝牙子进程下发以下默认配置：

```text
BLUETOOTH_DEVICE_HOST=192.168.4.20
BLUETOOTH_UDP_HOST=0.0.0.0
BLUETOOTH_UDP_PORT=5000
BLUETOOTH_CONTROL_PORT=5001
BLUETOOTH_CONTROL_POLL_SECONDS=0.5
BLUETOOTH_CONTROL_TIMEOUT_SECONDS=10
BLUETOOTH_TIME_SYNC_INTERVAL_SECONDS=5
BLUETOOTH_TIME_SYNC_MAX_AGE_SECONDS=30
```

Jetson仍然只需启动：

```bash
python3 start_edge.py
```

不得要求单独启动另一个蓝牙控制脚本。

### 7.4 `server.py`

可保留现有接口路径：

```text
POST /api/vehicles/{vehicle_id}/bluetooth/control
GET  /api/vehicles/{vehicle_id}/bluetooth/control/next
POST /api/vehicles/{vehicle_id}/bluetooth/control/ack
```

需要调整：

- `/bluetooth/timing` 标记废弃，确认没有调用后删除；
- 控制快照增加 `queued/delivering/applied/error/expired`；
- 增加命令过期时间；
- ACK 记录最终发送状态、Jetson 时间、设备 ACK 时间和错误原因；
- 新命令覆盖旧命令时明确将旧命令标记为 superseded；
- 计算延迟时优先使用 Jetson 上传的 `source_time_ms`；
- 保存 `sync_id`、`sync_rtt_ms`、`clock_offset_ms` 和 `latency_quality`；
- 对未来时间、过旧时间和负延迟进行校验，不使用 `max(0, ...)` 掩盖时钟错误。

### 7.5 `static/app.js` 和蓝牙页面

页面结构可以保持不变，但控制状态应修改为：

- 点击后按钮暂时禁用并显示“命令已排队”；
- 持续通过已有指标更新获取控制状态；
- 收到 `applied` 后显示“发送端已打开/关闭”；
- 收到 `error/expired` 后恢复按钮并显示具体原因；
- `agent_status=offline` 时说明 Jetson 控制代理离线；
- 不再出现“等待 Ubuntu 发送端连接云端”的描述；
- 延迟未同步时显示“待时间同步”，不能显示 0 ms。

### 7.6 K3 固件

必须实现：

- 监听 `192.168.4.20:5001/UDP`；
- 将 `BTCTL` 和 `BTSYNC REQ` 完整转发到连接 nRF52840 的 UART；
- 将 UART 收到的 `BTACK`、`BTSYNC RESP` 和遥测报文转发到 `192.168.4.100:5000/UDP`；
- 正确处理半包、粘包和 `#` 分隔；
- 不改变 `COMMAND_ID`、`SYNC_ID` 和时间字段；
- 可返回诊断 ACK，但诊断 ACK 不能冒充发送电脑的最终 ACK。

### 7.7 nRF52840 固件

必须实现：

- UART 收到 `BTCTL` 或 `BTSYNC REQ` 后通过 BLE Notify 发给发送电脑；
- BLE Write 收到遥测、`BTACK` 或 `BTSYNC RESP` 后完整转发到 UART；
- 同时处理 20 字节 BLE 分片与 `#` 帧重组；
- BLE 断开时保留 UART 接收能力并在重连后恢复 Notify；
- 不自行生成最终 `APPLIED` ACK；最终 ACK 必须来自 `ble_s32_sender.py`。

## 8. 对车身域和 WiFi 域方案的借鉴

### 8.1 借鉴车身域

可以直接借鉴：

- 网页创建带序号的待执行命令；
- Jetson周期轮询云端；
- Jetson通过独立 UDP 控制端口向板端下发；
- Jetson周期发送时间同步包；
- 板端遥测携带发送状态。

需要增强：

- 车身域当前在 Jetson 完成 `sendto()` 后即确认 delivered；
- 蓝牙域必须等待发送电脑返回匹配命令 ID 的真实 ACK；
- `sendto()` 成功只能表示本机内核接受了 UDP 数据，不能表示 K3、nRF 或发送电脑执行成功。

### 8.2 借鉴 WiFi 域

可以直接借鉴：

- 时间信息随业务报文经过完整数据链路；
- Jetson提取时间信息后统一上传；
- 云端分别展示发送端到 Jetson、Jetson到云端和总延迟。

不能直接照搬：

- WiFi发送电脑当前使用本机 epoch 时间，依赖时钟已经同步；
- 蓝牙发送电脑在隔离条件下应采用本文的四时间戳同步与 monotonic 映射；
- 当前 WiFi 域没有网页启停真实发送端的反向控制链路。

## 9. 安全与可靠性要求

- 云端 Token 只允许出现在 Jetson 和云端配置中；
- 发送电脑、K3、nRF52840 不保存云端域名和 Token；
- Jetson只接受来自 `192.168.4.20` 的 ACK/同步响应；
- 使用命令 ID、同步 ID、会话随机数抵抗旧报文重放；
- 控制帧和同步帧至少使用 CRC16 检错；
- 如果车辆网络可能被非授权设备接入，应进一步使用预共享密钥 HMAC；
- 日志不得打印 Token；
- UDP 重试必须保持命令 ID 不变；
- 所有解析器必须限制帧长度，建议不超过 512 字节；
- 未知帧、CRC 错误和来源地址错误只记录限速日志，不进入云端业务状态。

## 10. 实施顺序

### 10.1 第一阶段：只实现网页启停闭环

第一阶段不得同时开发 `BTSYNC`、`TICK_US`、时钟 offset 或端到端延迟算法。

1. 冻结 `BTCTL/BTACK` 协议、BLE UUID、UDP 5000/5001 和最大帧长度；
2. 修改 nRF52840 固件，实现控制帧的 UART → BLE Notify 和 ACK 的 BLE Write → UART；
3. 修改 K3 固件，实现 UDP 5001 → UART 下行以及 UART → UDP 5000 ACK 上行；
4. 使用本地工具验证 Jetson → K3 → nRF → 发送电脑以及 ACK 返回的双向通道；
5. 修改 `ble_s32_sender.py`，删除全部云端 HTTP 代码，实现 Notify 控制、实际启停和真实 ACK；
6. 修改 `bluetooth_edge_agent.py`，实现云端命令轮询、UDP 下发、重试、超时和 ACK 上报；
7. 修改 `start_edge.py`，加入蓝牙板地址、控制端口和控制超时配置；
8. 修改 `server.py`，实现 `queued/delivering/applied/error/expired` 状态；
9. 修改前端，使页面只在真实 ACK 后显示启停成功；
10. 添加控制相关自动化测试；
11. 在发送电脑无云端路由的环境中完成正常、断链、重试和重连测试；
12. 通过第 12.1 节阶段一验收门并更新启停功能文档。

第一阶段期间的延迟显示规则：

- 删除旧 `/bluetooth/timing` 直连调用；
- 保持遥测数据正常上行；
- 网页延迟显示“待时间同步”，不能保留旧旁路结果，也不能显示伪造的 0 ms。

### 10.2 第二阶段：实现端到端延迟

只有第一阶段验收通过后才能开始：

1. 冻结 `BTSYNC`、`SEQ/TICK_US/SYNC_ID` 协议；
2. 扩展 nRF52840 和 K3 固件，使同步请求与响应通过现有双向通道转发；
3. 修改 `ble_s32_sender.py`，响应同步请求并在遥测报文中加入单调时钟；
4. 修改 `bluetooth_edge_agent.py`，实现四时间戳同步、样本筛选和时钟映射；
5. 修改 `server.py`，计算并保存分段延迟、总延迟和质量字段；
6. 修改前端，显示有效延迟或明确的“待时间同步”；
7. 添加同步、漂移、异常时间戳和延迟计算测试；
8. 完成时钟漂移、同步过期、高 RTT 和链路重连验收；
9. 更新根目录 README 和 `bluetooth_gateway/README.md`。

### 11.3 物理链路证明

验收时应使用抓包和断链实验共同证明不存在旁路：

- 在发送电脑上抓包，运行 `ble_s32_sender.py` 期间不应出现访问云端域名/IP 的流量；
- 发送电脑不配置云端路由时，两项功能仍可工作；
- 拔掉 K3 网线后，网页控制必须失败；
- 断开 BLE 后，网页控制必须失败；
- 关闭 Jetson 蓝牙代理后，网页控制必须失败；
- 只有完整链路恢复后，命令才能成功并产生新 ACK。

## 12. 验收标准

### 12.1 第一阶段验收门：网页启停

1. `ble_s32_sender.py` 不包含任何云端 URL、Token 或 HTTP 客户端代码；
2. 发送电脑仅通过 BLE 与 nRF52840 通信；
3. 旧 `/bluetooth/timing` 旁路停止使用，延迟暂时显示待时间同步；
4. 网页命令依次经过云端、Jetson、K3、nRF52840 和 BLE 到达发送电脑；
5. 发送电脑实际修改发送状态后才产生最终 ACK；
6. 最终 ACK 沿 BLE、UART、K3、UDP、Jetson、HTTP 返回云端；
7. 任一硬件中间节点断开时，网页不得显示执行成功；
8. Jetson仍然只需执行 `python3 start_edge.py`；
9. 控制自动化测试和硬件断链测试全部通过。

只有以上九项全部通过，才允许开始第二阶段。

### 12.2 第二阶段验收门：端到端延迟

1. 第一阶段所有能力继续正常工作且无回归；
2. 每条有效延迟记录都来源于随业务报文传输的 `TICK_US` 和有效同步映射；
3. 无有效同步时不伪造端到端延迟；
4. 同步过期、高 RTT、异常时间戳和时钟跳变能够被识别；
5. 延迟自动化测试、时钟漂移测试和链路重连测试全部通过；
6. 发送电脑仍不存在任何云端直连流量。

## 13. 最终链路总结

```text
第一阶段——网页启停：
网页 → 云端 → Jetson → UDP 5001 → K3 → UART → nRF52840
  → BLE Notify → 发送电脑实际启停
  → BLE ACK → nRF52840 → UART → K3 → UDP 5000
  → Jetson → HTTP ACK → 云端 → 网页最终状态

第二阶段——端到端延迟：
发送电脑 monotonic 时间
  → BLE → nRF52840 → UART → K3 → UDP 5000
  → Jetson时间映射 → HTTP → 云端计算 → 网页
```

该方案消除了发送电脑到云端的直接旁路，使延迟和控制结果都能反映完整蓝牙域物理链路的真实状态。
